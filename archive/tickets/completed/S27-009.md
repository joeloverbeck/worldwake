# S27-009: Same-place concurrent violations remain distinct through investigation lifecycle

**Status**: ✅ COMPLETED
**Priority**: MEDIUM
**Effort**: Medium
**Engine Changes**: Yes — add unresolved-vs-resolved violation lifecycle so identity-bearing incidents remain investigable until their own commit
**Deps**: S27-004, S27-005, S27-008; spec `specs/S27-expectation-violation-goals.md`; `docs/golden-e2e-testing.md`

## Problem

The live code already carries violation identity end to end, but it does not yet prove or fully preserve the lifecycle needed for two same-place incidents to survive sequential investigation.

Today `GoalKind::InvestigateViolation { violation_id, place }` exists and the investigate payload is bound authoritatively to `violation_id`, but candidate generation still treats `ViolationMemory` primarily as a "noticed already, suppress re-emission" cache. That is enough to prove first-detection identity, but not enough to guarantee that a sibling same-place violation remains investigable after the first violation commits.

Without a focused lifecycle fix plus a golden proof, the architecture can still collapse into this failure mode:

1. two same-place violations are detected together
2. one violation is selected and investigated
3. the sibling incident stays recorded in memory but never re-enters goal generation
4. the agent never performs the second investigation even though the incident still exists

That is an architectural contradiction. A recorded violation should be a first-class incident with stable identity and explicit lifecycle, not just a one-tick emission guard.

## Assumption Reassessment (2026-03-25)

1. The original ticket assumption that the live engine still uses place-scoped `GoalKind::InvestigateMissing { place }` is stale. The live goal contract is `GoalKind::InvestigateViolation { violation_id, place }` in `crates/worldwake-core/src/goal.rs`, and planner payload synthesis preserves `violation_id` in `crates/worldwake-ai/src/goal_model.rs`.
2. The original `Engine Changes: None` scope is incorrect. Focused coverage already exists for identity-bearing detection and affordance binding:
   - `same_place_distinct_violations_emit_distinct_investigate_goals` in `crates/worldwake-ai/src/candidate_generation.rs`
   - `investigate_affordances_remain_distinct_for_same_place_violations` in `crates/worldwake-systems/src/investigate_actions.rs`
   Those tests prove initial distinctness, not sequential lifecycle persistence.
3. The live architectural gap is narrower and more precise than the original ticket narrative: `emit_expectation_violation_candidates()` in `crates/worldwake-ai/src/candidate_generation.rs` records new incidents and skips already-recorded ones, but it does not re-emit still-unresolved recorded violations. That means a sibling violation can disappear from AI selection after the first investigation completes.
4. `ViolationMemory` in `crates/worldwake-core/src/violation.rs` currently conflates "incident exists", "incident already noticed", and "incident should no longer be investigated". It stores expiry and identity, but no explicit resolution state for "this exact violation was already investigated".
5. `commit_investigate()` in `crates/worldwake-systems/src/investigate_actions.rs` currently refreshes TTL and records `SocialObservationKind::WitnessedAbsence`, but it does not explicitly mark the investigated violation as resolved. That prevents a clean unresolved-incident lifecycle and relies on suppression side effects instead of explicit state.
6. The right golden home is still `crates/worldwake-ai/tests/golden_emergent.rs`. The missing proof is cross-layer:
   - candidate generation / ranking -> decision trace
   - investigate start binding -> selected active action payload plus action trace
   - authoritative aftermath and incident lifecycle -> world/belief state
7. Replay convention in the live golden suite is not a special replay harness for this class of test. The existing pattern is "run the same scenario twice with the same seed and assert identical hashes/outcomes", which is already used across `golden_emergent.rs` and `golden_social.rs`.
8. `golden_entity_missing_discovery_does_not_teleport_belief` in `crates/worldwake-ai/tests/golden_social.rs` remains relevant but does not cover this ticket. It proves passive belief correction locality for one missing-entity discrepancy, not concurrent same-place violation identity through sequential investigate commits.

## Architecture Check

1. The cleaner architecture is to treat recorded violations as first-class incidents with explicit unresolved/resolved lifecycle, not as a one-shot suppression cache. That keeps identity, candidate generation, affordance binding, and authoritative action commit aligned around the same object.
2. This is better than a golden-only change because the current architecture has a production contradiction: identity-bearing incidents can exist in `ViolationMemory` yet become unreachable to AI planning after the first sibling commit.
3. This is better than a place-scoped workaround because the live engine has already moved to `violation_id` identity. Reintroducing place aliasing or fallback selection would regress the cleaner architecture already present in goal and action payload binding.
4. The robust long-term shape is:
   - detection creates a concrete recorded incident if none exists for that mismatch
   - unresolved recorded incidents remain candidate-eligible across ticks
   - authoritative investigate commit resolves exactly one violation id
   - resolved incidents still suppress immediate rediscovery until expiry, but no longer emit investigate goals
5. That lifecycle keeps the architecture extensible for future investigation aftermath, reporting, and evidence systems because "noticed", "still open", and "resolved" become explicit state instead of accidental byproducts of TTL refresh.

## What to Change

### 1. Add explicit violation resolution lifecycle

Update the violation-memory model so a recorded violation can remain present and identity-stable while also being marked resolved after its own investigation commits.

Required behavior:

1. Newly detected mismatches still allocate stable `violation_id`s.
2. Unresolved recorded violations remain eligible to emit `InvestigateViolation` goals across ticks.
3. Investigating violation `A` resolves only `A`, not sibling violation `B` at the same place.
4. Resolved-but-unexpired incidents still suppress immediate rediscovery of the exact same mismatch.

### 2. Preserve same-place sibling investigation through the AI pipeline

Update AI candidate generation so recorded unresolved violations continue to surface as investigation candidates even after the initial detection tick. Do not rely on the first detection tick being the only opportunity to plan against that incident.

### 3. Add end-to-end golden proof in `golden_emergent.rs`

Create a same-place concurrent-violation scenario with:

1. one investigator agent
2. one shared place
3. two stale beliefs at that same place
4. two concrete violated expectations with different kinds and different `violation_id`s
5. no unrelated higher-priority branches

Recommended concrete setup:

1. a believed-present entity that is moved away before observation
2. a believed-stocked local source that is depleted before observation

Assertions:

1. the first planning trace shows two distinct `GoalKind::InvestigateViolation` candidates sharing one place and differing by `violation_id`
2. the first started investigate action is bound to exactly one of those ids
3. after the first commit, only that violation is resolved and only that violation has `WitnessedAbsence` aftermath
4. the sibling violation remains unresolved and is later selected with its own bound `violation_id`
5. the final belief state contains two distinct `WitnessedAbsence` artifacts, one for each original violation subject

### 4. Add deterministic replay companion

Add the standard same-seed replay companion for the new scenario in `crates/worldwake-ai/tests/golden_emergent.rs`.

## Outcome

Completion date: 2026-03-25

What actually changed:

1. Added explicit unresolved/resolved lifecycle to `ViolationMemory`, so recorded incidents remain identity-stable while only unresolved incidents stay candidate-eligible.
2. Fixed the live runtime mismatch in expectation-violation detection by comparing stale beliefs against fresh local observation in `PerAgentBeliefView`, rather than against stale subjective occupancy/inventory reads.
3. Updated investigate commit semantics so authoritative completion resolves exactly one `violation_id` and leaves same-place siblings unresolved.
4. Added investigate identity to `ActionTraceDetail`, which made the new golden able to prove which concrete violation id reached authoritative commit.
5. Added the missing same-place concurrent-violation golden and replay companion in `crates/worldwake-ai/tests/golden_emergent.rs`.

Deviations from original plan:

1. The original ticket claimed "golden coverage only". Delivery required production changes in `worldwake-core`, `worldwake-sim`, `worldwake-systems`, and `worldwake-ai` because the live architecture had two real gaps: no explicit incident resolution lifecycle, and no fresh-local-observation surface for runtime violation detection.
2. The golden scenario uses two concurrent `EntityMissing` incidents at the same place rather than the originally suggested mixed `EntityMissing` + `SupplyDepleted` pair. That kept the scenario isolated on the incident-identity contract while avoiding unrelated live variability in the resource-source branch.
3. The final proof surface for exact investigate identity uses action-trace detail plus decision traces, which is stronger and cleaner than inferring identity indirectly from place-only aftermath.
