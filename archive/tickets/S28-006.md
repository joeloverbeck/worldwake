# S28-006: Extend trace dump with knowledge path output + workspace verification

**Status**: ✅ COMPLETED

**Deps**: S28-001, S28-002, S28-003, S28-004, S28-005

## Problem

The `dump_agent()` function in `decision_trace.rs` currently renders candidate evidence traces (contributors, exclusions) but not knowledge paths. After S28-002 through S28-005 populate knowledge paths across all candidate families, the trace output must render them in human-readable form for debugging emergence chains. This ticket also serves as the final workspace verification gate.

## Assumption Reassessment (2026-03-25)

1. `dump_agent()` at `decision_trace.rs:700` iterates candidates in the `PlanningOutcome` and calls formatting helpers. Currently renders evidence contributors and exclusions per candidate.
2. `PerceptionSource` at `belief.rs:626-631` has 4 variants: `DirectObservation`, `Report { from, chain_len }`, `Rumor { chain_len }`, `Inference`. Each needs human-readable formatting.
3. `InstitutionalKnowledgeSource` at `institutional.rs:172-182` has 4 variants: `WitnessedEvent`, `Report { from, chain_len }`, `RecordConsultation { record, entry_id }`, `SelfDeclaration`. The `learned_at` field is on `BelievedInstitutionalClaim` / `InstitutionalBeliefProvenance`.
4. `summary()` one-liner at `decision_trace.rs` should remain unchanged per spec.
5. `FeasibilityHint` from S25 is already on `RankedGoalSummary`. The spec asks knowledge path output to coexist with feasibility display in the candidate header — verify feasibility is already rendered or add it.
6. This is a diagnostic output ticket. No behavioral changes.

## Architecture Check

1. Rendering knowledge paths inside `dump_agent()` follows the existing pattern: iterate candidate evidence, format each entry. The new output appears after evidence lines and before the next candidate.
2. Format uses entity IDs directly (not names) in the trace — consistent with existing trace output which shows entity IDs. Name resolution is a separate concern.
3. No backward-compatibility shims.
