# S27-008: Thread stable violation identity through goals and investigate execution

**Status**: PENDING
**Priority**: HIGH
**Effort**: Large
**Engine Changes**: Yes — `worldwake-core` violation/goal identity, `worldwake-ai` investigation goal generation and binding, `worldwake-sim` payload/binding support, `worldwake-systems` investigate affordance and handler
**Deps**: S27-001, S27-002, S27-003, S27-004; spec `specs/S27-expectation-violation-goals.md`

## Problem

The live S27 pipeline now detects and records concrete expectation violations, but it still collapses distinct violations into a place-scoped investigation goal before execution. That means two different anomalies at the same place currently share one goal identity and the authoritative `investigate` handler resolves “the latest matching violation at this place” instead of the exact violation the planner selected.

That is workable for the first delivery of `investigate`, but it is not the ideal architecture. It weakens concrete-state traceability, makes same-place concurrent anomalies ambiguous, and creates the wrong foundation for future evidence, report, accusation, or repeated-investigation logic. The clean fix is to give each recorded violation stable identity and carry that identity all the way from violation detection to authoritative action commit.

## Assumption Reassessment (2026-03-25)

1. The current live identity boundary is `crates/worldwake-core/src/violation.rs`. `RecordedViolation` has `{ kind, observed_tick, expires_tick }` and `ViolationMemory::record()` deduplicates by `ViolationKind` only. There is no stable violation id today.
2. The current live goal under test is `GoalKind::InvestigateMissing { place }` in `crates/worldwake-core/src/goal.rs`. `GoalKey` therefore collapses investigation identity to place, not incident.
3. `emit_expectation_violation_candidates()` and `emit_violation_goal()` in `crates/worldwake-ai/src/candidate_generation.rs` emit investigation goals from `ViolationKind`, but the emitted goal keeps only `place`. Distinct `EntityMissing` and `SupplyDepleted` violations at the same place therefore collide at the goal layer.
4. `PlannerOpKind::Investigate` is already the live terminal operator in `crates/worldwake-ai/src/planner_ops.rs`, and `GoalKind::InvestigateMissing { place }` currently binds through place-only matching in `crates/worldwake-ai/src/goal_model.rs`. The present AI binding surface has no way to verify non-target payload identity for investigate.
5. The current authoritative handler in `crates/worldwake-systems/src/investigate_actions.rs` resolves local investigate state by scanning `ViolationMemory` for the newest matching violation at the actor's current place. This is the precise live ambiguity boundary.
6. `TargetSpec::ActorPlace` now exists in `crates/worldwake-sim/src/action_semantics.rs` and `crates/worldwake-sim/src/affordance_query.rs`, so place binding is no longer the architectural problem. The remaining problem is non-entity incident identity.
7. The current focused coverage proves investigate registration, start gating, duration resolution, commit aftermath, abort semantics, and place binding. It does not yet prove that two active same-place violations remain distinct through candidate generation, planning, and authoritative execution.
8. `specs/S27-expectation-violation-goals.md` still describes the goal family as `InvestigateMissing { place }`. That was acceptable for the first delivery, but once the same recorded violation needs durable identity, the name and data contract should be corrected rather than patched around.
9. FOUNDATIONS favors making the incident itself explicit over inferring it from a lossy summary. Principle 3 requires concrete state over abstract summaries, Principle 4 requires persistent identity, Principle 16 requires memories/evidence/records to exist as real state, and the compatibility ban in `docs/FOUNDATIONS.md` forbids preserving the place-only path as a parallel alias once the better design is introduced.
10. Mismatch + correction: this is not just an investigate-handler ticket and not just an action-payload ticket. The live ambiguity is created jointly by `ViolationMemory`, `GoalKind`, AI goal binding, and the authoritative investigate entrypoint. The fix must update the full chain.

## Architecture Check

1. The cleaner long-term design is to treat a recorded violation as a first-class incident with stable identity. That keeps investigation grounded in a concrete carrier of consequence rather than a place-only summary, which aligns with FOUNDATIONS Principles 3, 4, 15, and 16.
2. The cleanest rename is to replace the semantically leaky `GoalKind::InvestigateMissing { place }` with a violation-based goal such as `GoalKind::InvestigateViolation { violation_id, place }`. `SupplyDepleted` already uses the same goal family, so the current name is narrower than the live behavior.
3. If a place cache remains on the goal for locality and heuristic search, it must be explicitly treated as derived data. The authoritative identity is the violation id, not the place field.
4. The investigate action should carry exact violation identity through the regular action contract, not through handler-side “latest matching place” recovery. A payload-bearing investigate action is justified here because the missing fact is not an entity target and cannot be represented cleanly as a normal world-entity target.
5. No compatibility alias should preserve the place-only investigation path. Once stable violation identity exists, the old place-only goal and fallback resolution path should be removed and all callers updated.

## Verification Layers

## What to Change

### 1. Give recorded violations stable identity in `worldwake-core`

Add a stable `ViolationId` value type and store it on `RecordedViolation`.

Update `ViolationMemory` so it owns incident identity explicitly. The component should:

- allocate a new id when a newly discovered violation kind is first recorded
- refresh the existing record for the same still-active violation kind instead of creating a second id
- allocate a new id if the earlier record expired and the violation is rediscovered later
- expose exact-id lookup helpers needed by AI and authoritative investigate execution

If a monotonic allocator is kept inside `ViolationMemory`, it must remain deterministic and agent-local.

### 2. Replace place-only investigation goals with violation-aware goals

Rename the live goal family to reflect what the system actually investigates. A concrete target shape such as `GoalKind::InvestigateViolation { violation_id, place }` is preferred.

Update:

- `crates/worldwake-core/src/goal.rs`
- `GoalKey` extraction so distinct violation ids do not collapse into one key
- `crates/worldwake-ai/src/candidate_generation.rs`
- `crates/worldwake-ai/src/goal_model.rs`
- `crates/worldwake-ai/src/planner_ops.rs`
- `crates/worldwake-ai/src/goal_policy.rs`
- `crates/worldwake-ai/src/ranking.rs`
- `crates/worldwake-ai/src/feasibility.rs`
- `crates/worldwake-ai/src/failure_handling.rs`

The goal family must remain belief-driven and locality-preserving. The agent still discovers the violation locally; this ticket only stops the system from erasing the discovered incident identity before action selection.

### 3. Carry exact violation identity through the investigate action contract

Add a dedicated investigate payload in `worldwake-sim` for the non-entity incident identity, then update the investigate affordance/selection/start/commit path to require that payload.

The live action should:

- continue using actor-place targeting for the physical location
- carry `violation_id` through payload, not through handler-side inference
- validate at start and commit that the referenced record is still active and still matches the bound place
- reject stale, expired, or wrong-place investigate payloads cleanly

`ActionState::Investigate` should store the chosen violation id in addition to any resolved subject/source facts needed at commit.

### 4. Make AI binding payload-aware for exact investigate selection

The current `matches_binding()` surface only sees authoritative targets. That is sufficient for entity/place-bound actions, but not for investigate once the true identity lives in payload.

Add the minimum clean binding surface required so AI plan validation can verify both:

- the physical place target
- the exact `violation_id` payload

Do not paper over this by allowing any investigate payload at the same place. The point of the ticket is to remove that ambiguity.

### 5. Strengthen focused tests for same-place ambiguity

Add focused tests that prove:

- two active violations at the same place produce two distinct investigation goals
- starting investigate for one violation does not silently bind the sibling violation
- completing or blocking one violation does not suppress the other purely because the place matches
- re-observing the same still-active violation refreshes its record without allocating a second id
