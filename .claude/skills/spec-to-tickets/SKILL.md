# Spec to Tickets

Break a numbered spec into a series of small, actionable implementation tickets.

## Invocation

```
/spec-to-tickets <spec-path> <NAMESPACE>
```

**Arguments** (both required, positional):
- `<spec-path>` — path to the spec file (e.g., `specs/S05-merchant-stock-storage-and-stalls.md`)
- `<NAMESPACE>` — ticket namespace prefix (e.g., `S05MERSTOSTALL`)

If `<NAMESPACE>` is omitted, propose one derived from the spec number and abbreviated title (e.g., `S102-frontier-aware-exploration.md` → `S102FROAWAEXP`). Ask the user to confirm or override before proceeding. If `<spec-path>` is missing, ask the user to provide it before proceeding.

## Process

Follow these steps in order. Do not skip any step.

### Step 1: Mandatory Reads

Read ALL of these files before any analysis:

1. **The spec file** (from argument 1) — read the entire file
2. **`tickets/_TEMPLATE.md`** — the canonical ticket structure; every ticket you produce must follow this template exactly
3. **`tickets/README.md`** — the ticket authoring contract; understand the required sections and checks
4. **`docs/FOUNDATIONS.md`** — architectural commandments; every ticket must align with these principles. Skip if read earlier in this session and not modified since. If the file exceeds the Read tool's token limit, read the preamble and principle listing (first ~200 lines) using offset/limit, which covers the non-negotiable principles. The summary in `CLAUDE.md` (available via system context) supplements the direct read.
5. **`docs/precision-rules.md`** — precision rules for technical claims; governs Assumption Reassessment and Verification Layers sections. Skip if read earlier in this session and not modified since.

### Step 2: Codebase Validation

Before decomposing, validate the spec's assumptions against the actual codebase:

- **`git status` first** — Before any spec validation, run `git status` (and `git diff --stat` if changes exist) to surface uncommitted working-tree work. For each modified file that touches types/files referenced by the spec, note "in-progress on D<n>" against the relevant deliverable. Surface affected tickets in Step 4's summary Notes column (e.g., `partial in-progress in working tree`). The user may then mark such tickets `Status: COMPLETED` (work fully done) or `PENDING` (work continues from partial state). Do not silently re-author already-implemented work as net-new.
- **Grep/Glob** for file paths mentioned in the spec — confirm they exist
- **Grep** for types, functions, and modules the spec references — confirm they are real and current
- **Flag** any stale assumptions, missing files, or renamed entities
- For specs adding **new universal agent components**, grep `create_agent` in `crates/worldwake-core/src/world.rs` to check whether the bootstrap path seeds default values for existing universal profiles. If it does, the new component must also be seeded there, and the `world_txn.rs` `create_agent()` delta assertion must be updated. Include both in the ticket's Files to Touch and What to Change.
- If you find discrepancies, present them to the user before proceeding. Distinguish two tiers: (a) **path-level discrepancies** — specific symbol names, section numbers, line citations, or file-local identifiers that differ from current code but don't change deliverable shape — are safe to embed in the affected ticket's Assumption Reassessment and surface as a one-line entry in the Step 6 Notes block. (b) **Contract-level discrepancies** — the spec's deliverable mechanism, crate boundary, behavioral contract, or storage shape diverges from current code — warrant a hard-stop and `/reassess-spec` re-run before continuing. Under a session-level no-clarifications instruction (the user has asked you to work without stopping for clarifying questions), path-level corrections proceed silently with surfacing in Notes; contract-level corrections still warrant the hard-stop because they reshape ticket scope and the user's binary approval is the only signal that disambiguates the corrected decomposition.
- If `/reassess-spec` was run on this spec in the current session and all findings were resolved, Step 2 validation may be abbreviated to a spot-check of key references rather than a full re-validation. 3–5 targeted greps is sufficient. An abbreviated spot-check should verify at least:

  - **(a) Primary references**: the spec's primary type/function references still exist at the stated paths.
  - **(b) Serialization**: if the spec modifies serialized state or save/load paths, `SAVE_FORMAT_VERSION` hasn't changed since reassessment. Skip this check for specs that don't touch serialization.
  - **(c) Sibling specs**: no new files in `specs/` reference the same types.
  - **(d) Struct construction sites**: for specs that add fields to existing structs, grep for struct literal-opening construction sites (prefer `rg -n '^\s*<StructName>\s*\{$' <crate-path>` over the looser `rg -n '<StructName> \{'`, which matches return-type annotations like `fn x() -> StructName {` and overcounts by ~2–3× on factory-heavy modules) to verify all construction sites are accounted for in the tickets' Files to Touch. If the construction site count is high (>20), note the count in the Step 4 summary table's Notes column justification and consider whether the field-addition ticket should be split by crate. A high construction site count typically elevates effort from Small to Medium. When the raw construction-site count exceeds 15, OR the added fields lack a meaningful `Default` value (so construction sites must supply values explicitly regardless of count), run a spread-syntax spot-check before finalizing the effort classification: `rg -B 1 -A 1 '<StructName>\s*\{' <crate-path> | head -50` (or equivalent). If most sites use `..Default::default()` / `..StructName::default()` / spread syntax AND the added fields all have meaningful `Default` values, the count is informational — effort classification tracks semantic complexity rather than site count. If most sites explicitly enumerate fields without spread syntax, OR the added fields lack trivial defaults, the count is load-bearing and effort tracks it directly (>15 → Medium, >100 → Large). The 15-site lower bound exists because field-addition tickets in the 15–50 range routinely turn out to be load-bearing (most repos do not consistently use spread syntax), and surfacing the spread ratio at that band lets the Small/Medium/Large effort decision happen with evidence rather than guesswork. For counts above ~100 sites with no spread-syntax escape hatch, Large effort is typically warranted even when the work is mechanical, because review cost scales with touched-file count and the workspace-builds-after-each-ticket constraint prevents splitting. For specs adding fields to `AgentBeliefStore`, also check `BeliefStoreDiff` in `crates/worldwake-core/src/belief.rs` — it captures structural diffs for event-log delta compaction and may need corresponding diff fields for the new data. Additionally: if the modified struct derives `Serialize`/`Deserialize`, run a second grep pass over authored configuration files — `scenarios/**/*.ron`, plus any `**/*.toml` / `**/*.json` the workspace uses — for the struct's enclosing field name (e.g., `preference_profile:`) or the bare struct name. Authored configs that explicitly enumerate the struct's fields fail to deserialize when a non-`#[serde(default)]` field is added; include affected files in the ticket's Files to Touch unless the new field has `#[serde(default)]`. The blast radius for serialized structs always includes authored configs, not just Rust source. **Composite action registrations**: when the modified type is `ActionDef` or another shape registered through composite functions like `register_needs_actions`, `register_craft_actions`, `register_harvest_actions`, `register_office_actions`, or `register_artifact_actions`, the action-definition count expands by recipe/role/commodity multiplication and may dominate ticket effort — composites typically register 2–8 individual `ActionDef`s per public registration function, with recipe-driven composites scaling per-recipe. Cite both the registration-function count and the individual `ActionDef`-construction count in the Step 4 Notes column; let effort track the larger number. Parallel to `reassess-spec/references/codebase-validation.md`'s `Migration-scope claims for action registration` bullet — keep terminology consistent. **Enum-variant payload widening**: for cases where an existing enum variant changes shape (unit→struct, struct→tuple, adding fields to a tuple/struct variant), defer to sub-check (g)'s blast-radius analysis rather than running (d)'s struct-literal grep — the audit shape is the same (every existing construction/destructuring site needs migration), but the grep target is `EnumName::VariantName` workspace-wide, and the per-crate count determines whether the migration belongs in one ticket or splits across multiple.
  - **(e) Universal agent components**: for specs adding new universal agent components, verify whether `World::create_agent()` seeds defaults for existing universal profiles — if so, include the bootstrap seeding in the component-registration ticket. Separately verify whether `crates/worldwake-sim/src/world_txn.rs` carries a `create_agent` delta assertion (grep the file for `create_agent`): if it does, include the update in the same ticket; if no such assertion exists in the file, note "no world_txn.rs delta assertion to update" in the spot-check inline summary and proceed without forcing the update. The absent-file case is normal — not every sim-crate revision carries this assertion.
  - **(f) Existing tests**: for specs modifying existing functions, grep the target module's `#[cfg(test)]` block for test names exercising the changed functions (not just sibling `tests/*.rs` files — the target module's own inline tests matter too). Record existing test names for inclusion in ticket Assumption Reassessments during Step 5 — this moves discovery to the validation phase where it's sequential, so results are available during parallel ticket writing.
  - **(g) Rename/removal blast radius**: for tickets that rename or remove a type, function, field, or schema-generated accessor, grep workspace-wide (`crates/`, `tests/`, and any other Rust source roots) for every symbol being renamed or removed — including macro-generated accessor variants (e.g., `get_component_X`, `insert_component_X`, `iter_Xs`, `entities_with_X`, `query_X`, `count_with_X`, plus struct/enum name and any value-wrapping helper like `sample_X`). Count sites per crate. If any crate has >0 sites but is not in the ticket's Files to Touch, either (i) add the crate's files to Files to Touch, or (ii) split those sites into a dedicated follow-up ticket with an explicit dependency. Common miss targets: `worldwake-sim`, `worldwake-systems`, `worldwake-cli/src/bin/observer.rs`, `worldwake-cli/src/handlers/*`, and every `tests/` directory across the workspace. The per-crate count is what distinguishes a renamed-type ticket from a net-new-type ticket — the former always has a blast radius, the latter typically doesn't. **Variant additions to cross-crate enums** follow the same blast-radius analysis as renames — grep workspace-wide for exhaustive `match` arms (`<Enum>::<Variant>\s*=>` patterns) that destructure the enum, count per-crate, and add the new variant to the effort estimate. Sites using `_ =>` catch-all do not require a new arm but should be reviewed for whether catch-all semantics match the new variant's intent. This complements Step 3's "Cross-crate variant payload widening" (which covers shape *changes* to existing variants) and "Forward-declared enum variants" (which covers declaration-without-emission timing) by addressing the pure addition case.
  - **(h) Generated documentation**: if a script regenerates documentation from the modified struct's schema (e.g., `docs/profiles/all-profiles.md`, `docs/generated/*`), include the generated file plus the regeneration command in the ticket's Files to Touch. Look in `scripts/` for `*_docs.py` / `*_inventory.py`-style generators that consume the source crate. Adding a profile field without regenerating the doc leaves the doc and code inconsistent — and the doc-regen step is invisible to the Rust struct-literal grep used by sub-check (d).
  - **(i) Core-resident types with non-core field types**: for any new ECS component or core-resident struct the spec proposes, grep its field types and verify each resolves to a `worldwake-core` symbol. If a field type lives in `worldwake-sim`, `worldwake-systems`, `worldwake-ai`, or `worldwake-cli`, flag as an emergent migration: either (a) relocate the referenced type to core in the foundation ticket's scope (and run cross-crate consumer analysis on all import sites), or (b) introduce a core-side `*Tag` mirror per `reassess-spec/references/worldwake-validation-patterns.md::Core-Side Mirror Enum Pattern`. The decision routes through the spec's existing FOUNDATIONS alignment — relocation is cleaner when the referenced type carries no higher-crate behavior; the mirror pattern is cleaner when relocation would have a large blast radius or when the type carries non-`Copy` payload. Surface in the Step 4 summary Notes column so the user sees the emergent scope before tickets are written. This is the spec-to-tickets backstop for cases where reassess-spec's Core-Side Mirror Enum Pattern check didn't fire — the consequence surfaces here as an emergent migration at ticket-composition time.

  After the spot-checks, render the exercised sub-checks as a compact inline list before moving to Step 3 (e.g., `Spot-checks: (a) ✓, (b) ✓, (c) skipped — no new sibling specs, (d) 164 sites flagged, (e) N/A, (f) ✓, (g) N/A — no renames, (h) regenerated profile-doc added to Files to Touch, (i) ✓ — all field types resolve to core`). This proves each applicable sub-check ran and surfaces N/A cases explicitly.

  **(f) checkpoint**: Before emitting the spot-check inline summary, if (f) fired for any deliverable (the spec modifies existing functions exercised by inline `#[cfg(test)]` tests), list the existing test names found per affected module — `<module>: <test_name_1>:<line>, <test_name_2>:<line>` (preferred when the line-number information is available without extra tooling cost — typical `awk`/`grep -n` test enumeration produces line numbers natively). The bare-name form `<module>: <test_name_1>, <test_name_2>` is acceptable when line numbers are not readily available, but the line-number variant is preferred because it lets the implementer Read precisely the test under modification rather than re-grepping during ticket reassessment. Deferring (f) results to ticket-body placeholders like `(named during reassessment)` is not a substitute and will leave implementation tickets with implicit homework. The grep cost is paid once during Step 2; deferring it forces the same grep to be re-run during every ticket's `/implement-ticket` reassessment.

  **Auto-mode checkpoint**: If auto mode is active and all spot-checks passed (no Issue findings, no stale references, no missing files, no renamed symbols, no deferred reassessment findings), proceed directly to Step 4's auto-approval branch — emit the Step 4 summary inline (as decision-traceability) but do not pause for user approval — write tickets in the same turn. The auto-mode interaction rule at the end of Step 4 is binding here; making the decision at this point (when the no-Issues condition is freshest) avoids a redundant round-trip in Step 4.
- If `/reassess-spec` was run but some findings were deferred by the user, treat deferred items as out-of-scope for ticket decomposition. Note them in the Step 6 final summary as "deferred reassessment findings that may warrant separate tickets." Do not silently incorporate deferred findings into ticket scope.

### Step 3: Decompose the Spec

Analyze the spec and identify discrete work units:

- Each ticket must represent a **reviewable diff** — small enough for comfortable manual review
- Map **dependencies** between tickets (which must be done before which)
- Determine **priority ordering** (what to implement first)
- Ensure **every spec deliverable is covered** — no silent skipping. If a deliverable seems wrong or unnecessary, flag it to the user using the 1-3-1 rule instead of omitting it. Deliverables that explicitly state no changes are needed (e.g., "No new profile", "No new components") do not require tickets. Note their existence in the Step 4 summary if non-obvious.
- **Distributed deliverables**: when a deliverable's implementation is structurally inseparable from other deliverables (e.g., a cross-cutting read-access pattern that lands naturally inside multiple feature tickets, or a conceptual distinction whose mechanics materialize across several tickets), mark it "distributed" rather than either creating a redundant ticket or silently omitting it. In the Step 4 Scope column, name the distributed deliverable alongside the primary scope (e.g., `Scope: D3+D4, plus D8 (distributed — cross-ticket)`). In the Step 6 coverage mapping, use `D8 → 003+005+007 (distributed — no dedicated ticket; rationale: <one-line reason>)`. Render the ticket list as `+`-joined IDs followed by a single parenthetical rationale; do not insert per-ticket descriptions inside the list (e.g., write `D10 → 004+009+010 (distributed — split across belief-view, candidate emission, and ranking per phase-distinction rule)`, not `D10 → 004 (belief-view), 009 (emission), 010 (ranking) — split across three tickets`). Per-ticket descriptions belong in the Step 4 summary table's Notes column or in each ticket's body, not in the coverage mapping — keeping the mapping `+`-joined makes it grep-friendly for downstream tools and consistent across decompositions. A distributed deliverable is never a substitute for silent skipping — the rationale (why dedicated-ticket placement would be redundant or non-compile-safe) must be stated, and every ticket that contributes to the deliverable must have the deliverable number in its Scope column.
- **Split deliverables**: when a single deliverable cleanly partitions across multiple tickets (e.g., per-category, per-crate, per-domain, per-phase / lifecycle stage) and each ticket fully owns its slice, mark it "split" rather than "distributed." A per-phase split is a common pattern when a deliverable spans both type definitions (owned by a foundation ticket) and runtime behavior that consumes those types (owned by a downstream ticket); each ticket fully owns its phase-slice, even though "type defs" and "runtime behavior" are not category/crate/domain axes. This also covers the case where a struct's derived-view method signature references types defined in a sibling ticket — the method (signature plus body) defers to the ticket that introduces the parameter types, while the struct, storage, and store API remain in the foundation ticket. Render the coverage mapping as `D<n> → A+B (split — partitioned by phase: struct/store-API in A, derived view in B)`; treating the deferral as a Notes-block implementation note rather than a split leaves the mapping inaccurate, because the derived view is part of the deliverable, not commentary on it. Split differs from distributed in ownership: split deliverables have a per-ticket owner with a partitioned scope (each ticket fully implements its slice); distributed deliverables have no dedicated owner per ticket (each ticket implicitly contributes to a shared concept). In the Step 4 Scope column, name the slice in the primary scope (e.g., `Scope: D5 — combat.rs (7 actions)`). In the Step 6 coverage mapping, render as `D5 → 003+004+...+009 (split — partitioned by <axis>)` — `+`-joined IDs with a parenthetical naming the partition axis (file, crate, action category, domain, lifecycle phase). The split classification preserves the per-ticket owner relationship that distributed loses, which matters for the downstream `/implement-ticket` flow where each ticket reads its slice as its primary scope.
- **Subsumed deliverables**: when a deliverable's implementation lands fully inside exactly one other ticket as a trivial side-effect of that ticket's primary work (e.g., a `#[serde(default)]` annotation that rides along on the field-addition that defines the type, or a one-line config-key registration that lands as part of a larger struct extension), mark it "subsumed" rather than "distributed" (which is plural-ticket: `D8 → 003+005+007`) or "split" (which is per-ticket-owner with a partitioned scope). Subsumed differs from both: a single host ticket fully owns the deliverable, but the deliverable is not the host ticket's primary scope — it is absorbed as a side-effect. In the Step 4 Scope column, the host ticket's primary scope already covers the deliverable; in the Step 6 coverage mapping, use `D8 → 001 (subsumed — <one-line rationale>)`. Reserve subsumed for genuinely trivial absorption; if the host ticket would need to grow a sub-section in its What to Change to accommodate it, prefer a dedicated ticket instead.
- **Automatic deliverables**: when a deliverable is satisfied automatically by existing infrastructure once a sibling deliverable lands (e.g., observer/decision-trace surfaces that already iterate `EventTag` will render new event tags the moment they are added, with no observer-side code change), mark it "automatic" rather than either creating a no-op ticket or silently omitting it. In the Step 4 Scope column, name the automatic deliverable alongside the host ticket's primary scope (e.g., `Scope: D7+D10, plus D11 (automatic — observer renders new EventTag variants via existing infrastructure once D4 lands)`). In the Step 6 coverage mapping, use `D11 → 004 (automatic — <one-line rationale naming the existing infrastructure>)`. The host ticket should also list the deliverable in Out of Scope with a one-line note explaining the automatic coverage, so reviewers of the host ticket understand the deliverable was acknowledged. An automatic deliverable is never a substitute for silent skipping — the rationale must name the specific existing infrastructure that handles it (mirroring the "distributed" rationale requirement). Use this classification only when truly no code change is needed; if even a single line of new wiring is required, the deliverable belongs in a dedicated or distributed ticket instead.
- **Placeholder-replace pattern**: when a ticket defines a stub, baseline, or simplified path that a later ticket must replace to complete the semantic contract (common for compile-safe intermediate states where the real logic depends on later-ticket scope), make the relationship explicit in both directions: (a) name the placeholder in the earlier ticket's What to Change as "placeholder, replaced by ticket <later>" with a one-line description of what the placeholder does vs. what the real implementation will do, (b) list the replacement target as an Out of Scope item in the earlier ticket referencing the later ticket, and (c) reference the placeholder in the later ticket's What to Change with text like "Update ticket <earlier>'s placeholder `<symbol>`". This prevents reviewers of the earlier ticket from misreading the stub as the final contract and makes the dependency visible in both directions of the ticket sequence.
- Consider natural boundaries: type changes, new modules, test suites, integration points. When tests exercise multiple deliverables simultaneously and cannot be split per-deliverable, a single test ticket depending on all implementation tickets is a valid decomposition. Note the multi-dependency in the Step 4 summary
- When multiple spec deliverables share the same file set and cannot compile independently, merge them into a single ticket. Note merged deliverables in the Step 4 summary table notes
- Use the spec's "What This Does NOT Change" or equivalent non-goals section to populate tickets' Out of Scope fields — these are pre-validated non-goals from reassessment
- Ensure **workspace builds after each ticket** — if removing types/functions from a shared crate, all consumers must be updated in the same ticket. Splitting a migration across tickets is only valid when intermediate states compile.
  - **Required-field migrations**: when the spec adds a required (non-`Option`) field to an existing struct without a meaningful `Default`, the foundation ticket must populate all construction sites in one shot. Introduce a placeholder constructor (e.g., `Type::empty()` or a const literal) on the new field's type so the foundation ticket compiles; subsequent per-category tickets replace the placeholder with real values. Mark the placeholder per the existing Placeholder-replace pattern — name it in the foundation ticket's What to Change as "placeholder, replaced by tickets <list>" with a one-line description of what the placeholder does vs. what the real per-category implementations will populate.
  - **FND-28-driven combining**: beyond compile-block merges, combine deliverables when splitting them would leave a transient dead-code state in live authoritative paths (e.g., "switch consumer + delete old" tickets where the old code becomes unreachable but is not yet deleted). Note the FND-28 motivation in the Step 4 Notes column or in the combined ticket's Architecture Check section. This avoids the worst-of-both-worlds state where the workspace compiles but the live authority path carries unreachable fallback code waiting for a future deletion.
  - **Forward-declared enum variants**: adding a new variant to an enum in one ticket is acceptable even when the variant's emission sites land in a later dependent ticket, provided (a) the variant's semantics are documented at definition time, (b) the dependent ticket is named explicitly as the emission-site owner, and (c) no exhaustive match in the workspace breaks compilation when the new variant is added. The "transient dead-code state" rule (FND-28-driven combining above) applies to control-flow code that becomes unreachable, not to enum variants that are declared but not yet emitted — variants are declarations, not code paths. Document the forward-declared status in the host ticket's What to Change under the new variant's definition, naming the emission-site ticket explicitly.
  - **Cross-crate variant payload widening**: when a spec widens an existing enum variant (unit→struct, struct→tuple, or adding fields to an existing tuple/struct variant), the variant shape change AND all consumer construction/destructuring sites must land in one ticket — intermediate states fail to compile because the variant's constructor and pattern arity change atomically. Use sub-check (g)'s blast-radius site count to size effort. The new payload type's foundation (the type definition itself, e.g. a new struct introduced by the widening) may live in a separate prerequisite ticket; the widening + consumer migration is one downstream ticket. Prefer `#[serde(default)]` on the new fields so save-load deserialization tolerates pre-bump byte streams without a custom `Deserialize` impl.
  - **Variant subsumption consumer audit**: when a spec subsumes N legacy variants into 1 new variant (e.g., 3 → 1 rename + subsumption, common for "rename `AlternateTarget` → `RebindTarget`; merge `AlternateMerchant` and `AlternateRecipe` into it" patterns), grep workspace-wide for equality checks (`<enum> == <Enum>::<LegacyVariant>`) and pattern matches against each legacy variant. The migration ticket's `Files to Touch` enumerates the *construction* sites; this audit catches *dispatch* sites that bare-variant equality or pattern-match the legacy variant. Each dispatch site dispatching on the legacy variant must be reassessed for whether its original semantic intent is preserved by the broader new variant or requires a disambiguating predicate over the payload (e.g., `<payload_field>.is_some() && <other_payload>.is_none()`). Surface affected sites in the migration ticket's Assumption Reassessment as an adjacent-contradiction classification with the corrected predicate documented in What to Change. Variant subsumption is FND-28-compliant (preferred over deprecated wrappers), but the consumer-side semantic-shift risk is easy to miss because struct-literal grep for the new variant's name doesn't surface dispatch sites for the legacy names.
  - **Spec-vs-codebase storage contradiction**: when the spec proposes a field type that is incompatible with the host type's existing construction pattern (e.g., `Vec<T>` field on a struct used in `static` initializers; `Cow<'static, T>` on a `Copy`-deriving enum; lifetime-bound type stored as a struct field), the ticket reassessment picks the closest-compatible alternative (`&'static [T]`, an owned `Box<T>`, or a const-evaluable equivalent) and documents the design tension in the ticket's Architecture Check. The spec text should be updated on next reassessment if the alternative warrants — but the ticket proceeds with the construction-compatible storage rather than blocking on a spec-text fix. This is a path-level discrepancy per Step 2's two-tier classification (storage shape can change without changing the deliverable's contract or crate boundary), so under a no-clarifications instruction the alternative is picked silently with surfacing in the Step 6 Notes block.
- When all deliverables modify the **same file**, decompose by logical section or feature, not by file boundary. Each ticket targeting a different section of the same file is a valid reviewable diff. Note the shared file in the Step 4 summary rather than repeating it per-ticket.
- For **mechanical refactoring specs** (trait decomposition, enum splitting, interface migrations), recognize that multiple tickets may share an identical file set. In the summary table (Step 4), note the shared file set once and reference it from each ticket rather than forcing each ticket to independently discover the same list. Individual tickets should list only *additional* files beyond the shared set.

### Step 4: Present Summary for Approval

**Before writing any ticket files**, present a numbered summary table:

```
| # | Ticket ID | Title | Scope | Effort | Deps | FND | Notes |
|---|-----------|-------|-------|--------|------|-----|-------|
| 1 | <NS>-001  | ...   | <5-10 word scope> | Small  | None | — | — |
| 2 | <NS>-002  | ...   | <5-10 word scope> | Medium | 001  | P12,P27 | 34 construction sites |
| ...
```

Column roles:

- **Title** — human-readable ticket name (e.g., "Anomaly infrastructure and multi-agent rendering"). Matches the first-line `# <PREFIX-NNN>: <title>` that will be written to the ticket file in Step 5.
- **Scope** — deliverable mapping (e.g., "D1+D6") or acceptance surface (e.g., "adds detector X, emits anomaly Y"). For deliverables marked "distributed" or "automatic" (per Step 3's classifications), name them alongside the primary scope with the classification tag in parentheses (e.g., `D7+D10, plus D11 (automatic — observer renders new EventTag variants once D4 lands)` or `D3+D4, plus D8 (distributed — cross-ticket)`). Title and Scope should NOT duplicate each other; Scope answers "which spec pieces does this cover?" while Title answers "what is this ticket called?".
- **FND** — optional; populate only for tickets with notable FOUNDATIONS concerns (e.g., a ticket touching derived views should note P27). Use `—` for tickets with no specific concern.
- **Notes** — construction site counts, merged deliverables, shared file sets, or other decomposition-relevant details that don't fit in other columns.

If all tickets are independent, state this once rather than repeating `None` in every Deps cell. The Step 6 dependency graph can be a single sentence (e.g., "All tickets are independent — implement in any order").

**Wait for user approval or adjustments.** Do not write files until the user confirms.

**Auto mode interaction**: When auto mode is active and Step 2 validation surfaced no Issues (no stale references, no missing files, no renamed symbols, no deferred reassessment findings), auto-approve the summary table and proceed to Step 5. Announce the auto-approval inline (e.g., "Auto mode: no Issues surfaced in Step 2, proceeding to Step 5"). If Step 2 surfaced any Issue, the wait-for-user gate applies even in auto mode.

### Step 5: Write Ticket Files

For each approved ticket, write a file to `tickets/<NAMESPACE>-<NNN>.md` using the **exact structure** from `tickets/_TEMPLATE.md`.

Every ticket MUST include:

- **Status**: PENDING
- **Priority**: HIGH / MEDIUM / LOW (based on dependency order and criticality)
- **Effort**: Small / Medium / Large. Rough rubric: **Small** = 1-2 files modified, ≤3 new focused tests, no existing-test rewrites. **Medium** = 2-3 files, 3-6 new tests, ≤2 existing tests extended. **Large** = 4+ files, 6+ new tests OR ≥3 existing tests requiring extension, OR cross-module action-handler coordination. Boundaries are soft — calibrate against semantic complexity, not raw counts. Construction-site-driven elevation (per Step 2 sub-check (d)) overrides this rubric when triggered. FND-28-driven combining (per Step 3's combining rule) typically elevates a combined ticket's effort to Large because the combined surface spans both the new mechanism and the simultaneous deletion of the old path, often across multiple modules with cascading test updates — calibrate accordingly when bundling deliverables under the combining rule.
- **Engine Changes**: None or list of affected areas
- **Deps**: Other tickets or specs this depends on
- **Problem**: What user-facing or architecture problem this solves

#### Batch All Write Calls in One Message

Send **one assistant message containing one Write tool call per ticket**, not N sequential messages. Each ticket file write is independent because each creates a new file, so they can run concurrently. A single message with N Write calls costs one round-trip; N sequential messages cost N round-trips. Compose every ticket's full content first, then emit all Write calls in one batch.

For spec decompositions producing large tickets (individual contents >5KB), the rule still applies — the composition cost is paid once regardless of message count, so the latency saving is the dominant factor.

After the parallel batch returns, verify every ticket file was created. If any Write call failed (typo in path, permissions error, or other I/O failure), retry that ticket with the corrected argument immediately — do not proceed to Step 6 until all ticket files exist at their intended paths.

### Step 6: Final Summary

After writing all files:

1. **Verify cross-ticket dependency consistency**: For each `Deps` reference, confirm the depended-on ticket actually produces what the dependent ticket needs (types, modules, files). If a dependency is broken (e.g., ticket 005 depends on a type from 003 but 003's scope doesn't define it), flag the inconsistency.

2. **Deliverable coverage mapping**: List each spec deliverable and the ticket that covers it (e.g., `D1→001, D2→001, D3→002`). Verify all spec deliverables are accounted for. If any deliverable is missing, flag it before finalizing. If the spec uses phases or named sections instead of numbered deliverables (e.g., `Phase 2a`, `Layer 0`), adapt the coverage mapping to use the spec's organizational scheme — the `D1→001` format is illustrative, not prescriptive. When the spec uses named sub-sections without explicit D-keys (i.e., sub-section headers like `### worldwake-ai::opportunity_compiler (new module)` rather than pre-numbered `### D1: …`), the audit may assign sequential D-keys by `## Deliverables` sub-section order and declare the convention at the top of the Deliverable Coverage Mapping (e.g., `D-keys assigned by sub-section order: D1 = opportunity_compiler, D2 = effect_schema_index, …`). #### Save-format bump merge-note placement

Sub-check (b) determines whether the spec touches serialization. The placement of the merge note depends on whether the bump is single-ticket or multi-ticket; treat this as a binary rule rather than a free-form judgment:

- **No serialization impact (sub-check (b) found nothing)** — OMIT the Step 6 `### Merge-Order Constraints` heading. No merge note required anywhere.
- **Single ticket bumps `SAVE_FORMAT_VERSION` (no cascade)** — OMIT the Step 6 `### Merge-Order Constraints` heading. ## Constraints

- **FOUNDATIONS alignment**: Every ticket must respect the principles in `docs/FOUNDATIONS.md` (maximal emergence, belief-only planning, system decoupling, no backward compatibility, etc.)
- **Template fidelity**: Every ticket must use the `tickets/_TEMPLATE.md` structure exactly — no ad-hoc sections or missing required fields
- **Ticket fidelity**: Never silently skip a spec deliverable. If something seems wrong, use the 1-3-1 rule (1 problem, 3 options, 1 recommendation) and ask the user
- **Codebase truth**: File paths and type references in tickets must be validated against the actual codebase, not assumed from the spec
- **Reviewable size**: Each ticket should be small enough to review as a single diff. When in doubt, split further
- **Explicit dependencies**: Use the `Deps` field to declare inter-ticket dependencies; never leave implicit ordering
- **Performance-optimization specs**: For P12-type specs that compress computation without changing world meaning, tickets should include regression guard acceptance criteria with concrete metric thresholds. The metric should match what the spec actually optimizes — e.g., candidate count per expansion, expansion count, branching factor, or wall-clock time — not necessarily wall-clock time alone, which may be non-deterministic or platform-dependent. Include regression guard commands (e.g., soak seed runs, candidate-count assertions in golden tests). Acceptance criteria should distinguish correctness (golden tests pass) from performance (metric thresholds met)
